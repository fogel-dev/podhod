# Подход

Mobile-first приложение для тренировок. Один репозиторий, два независимых приложения:

```text
apps/
  web/          React + TypeScript + Vite, FSD
    src/app/    запуск и глобальные стили
    src/shared/ общие ресурсы
  api/          Go HTTP API
    cmd/api/    точка входа
    internal/   конфигурация и HTTP-сервер
design/         согласованный интерактивный макет; не входит в приложение
docs/           требования, дизайн, архитектурные решения
```

## Локальный запуск

Node.js 22.20.0, npm 11.6.1, Go 1.27.2. Docker нужен только для контейнерного запуска.

В корне:

```sh
npm ci
npm run dev
```

Во втором терминале:

```sh
cd apps/api
go run ./cmd/api
```

Фронт: http://127.0.0.1:5173. Vite пересылает `/api` в Go на `127.0.0.1:8080`. `GET /api/health` проверяет процесс; `GET /api/ready` — доступность PostgreSQL и применённость миграций без раскрытия подключения. Начиная с EGO-19 запуск API требует `DATABASE_URL` либо `DATABASE_URL_FILE`; секреты хранятся вне репозитория.

Для текущего Windows-окружения SDK Go скачан в игнорируемую `.tools/go`. Если Go ещё не установлен в PATH, из `apps/api` можно запускать `../../.tools/go/bin/go.exe run ./cmd/api`. Для других компьютеров SDK устанавливается отдельно.

API читает `HTTP_ADDR` из окружения; по умолчанию `127.0.0.1:8080`. `.env.example` — справка, файл `.env` автоматически не загружается. В PowerShell: `$env:HTTP_ADDR = '127.0.0.1:8080'`.

Начиная с EGO-21 API также требует `AUTH_HMAC_KEY` либо `AUTH_HMAC_KEY_FILE` (случайные 32 байта в hex) и `PUBLIC_ORIGIN`. `node tooling/dev/secrets.mjs` создаёт ключ вне checkout. Для Vite задайте origin `http://127.0.0.1:5173` и `AUTH_INSECURE_LOCAL=1`; этот режим разрешён только для HTTP loopback и использует отдельную dev-cookie. В production нужен HTTPS origin без пути, `AUTH_INSECURE_LOCAL` не задаётся, cookie имеет Secure/HttpOnly и префикс `__Host-`. `API_DEV_UPSTREAM` позволяет направить Vite на другой локальный порт API.

В интерфейсе доступны регистрация, вход, настройки аккаунта, часового пояса, пароля и отзыв устройств. Регистрация создаёт реальные пустые аккаунты, без demo данных; почта неподтверждённая. Для входа используйте логин, а не email. Сброса по почте пока нет; пароль рекомендуется сохранять в менеджере паролей. Не вводите реальные данные в интеграционные тесты.

## Проверки и сборка

```sh
npm run check
npm run build
npm run preview
```

Из `apps/api`:

```sh
go vet ./...
go test ./...
go build -trimpath -o bin/api ./cmd/api
```

`npm run format` форматирует новые исходники и документы; дизайн-прототип исключён. Go форматируется через `gofmt -w .` из `apps/api`. GitHub Actions проверяет оба приложения и контейнерные сборки отдельно.

## Контейнеры и деплой

```sh
export PODHOD_SECRETS_DIR="/tmp/podhod-dev-secrets"
export PODHOD_MEDIA_DIR="/tmp/podhod-dev-media"
node tooling/dev/secrets.mjs
docker compose up --build
```

В PowerShell задайте `$env:PODHOD_SECRETS_DIR = Join-Path $env:TEMP 'podhod-dev-secrets'` и `$env:PODHOD_MEDIA_DIR = Join-Path $env:TEMP 'podhod-dev-media'`, затем выполните команды `node` и `docker compose`. На Linux заранее создайте media каталог с владельцем 65532:65532 и mode 0700. Скрипт создаёт случайные пароли вне репозитория, не печатает и не заменяет существующие значения. Это каталоги для разработки; production требует постоянных защищённых каталогов и внешних резервных копий БД, фото и секретов. При запуске Go напрямую задайте абсолютный MEDIA_DIR и JOB_ENCRYPTION_KEY_FILE вместе с auth/database переменными из apps/api/.env.example.

Compose запускает PostgreSQL в закрытой сети, создаёт отдельные login/runtime роли и применяет миграции перед API. Вне Compose администратор выполняет `apps/api/db/bootstrap.sql`, создаёт login роли и выдаёт членство в `podhod_migrator`, `podhod_api`, `podhod_worker`. `go run ./cmd/migrate` запускается с migration подключением, API — с runtime подключением. Миграции встроены в binary, сериализуются advisory lock и проверяются по SHA-256; изменять применённые файлы запрещено.

Для интеграционных тестов `TEST_DATABASE_URL` указывает на отдельный тестовый PostgreSQL с административными правами. Тесты создают/удаляют только базы `podhod_test_*`; в CI эта база запускается отдельным service. Не использовать production подключение для тестов.

Compose также запускает `cmd/worker` с отдельной ролью PostgreSQL и `JOB_ENCRYPTION_KEY_FILE`. Очередь участвует в транзакции API; payload зашифрован AES-GCM, после завершения или окончательной ошибки удаляется. Worker использует lease с продлением, token для защиты от устаревшего обработчика и повторы с задержкой, максимум восемь попыток. Бизнес-обработчики подключаются в своих задачах; неизвестный вид задачи завершается явной ошибкой. Каждый обработчик обязан соблюдать отмену context и задавать таймауты внешним операциям. Доставка внешних действий допускает повтор после падения процесса.

Приложение открывается на http://127.0.0.1:8080, `/api` проксируется в Go. Frontend и API имеют отдельные Dockerfile с контекстом из корня: их можно собирать и выкатывать независимо из одного репозитория. API не публикуется наружу в Compose. `API_UPSTREAM` задаётся при запуске web-контейнера; секреты не нужны для сборки фронта. Для выпуска потребуются домен, TLS на внешнем reverse proxy и окружение хостинга; автоматического деплоя пока нет.

## Границы текущего этапа

Инициализированы сборки, проверки, глобальные стили, шрифты и сервер; добавлены OpenAPI/DTO и основа PostgreSQL с миграциями доступа/очереди/синхронизации. React содержит подключённые к API экраны регистрации/входа и настройки аккаунта; тренировочные экраны появятся в своих задачах. Нет моков, seed-данных и фиктивных CRUD. PWA manifest, service worker, установка и Web Push будут реализованы и проверены в EGO-8/EGO-16; нынешняя сборка ещё не является готовой PWA.

Схема FSD и причины выбора монорепозитория: [ADR-001](docs/adr/001-monorepo.md). Дизайн: [docs/design.md](docs/design.md). Статусы работы: [Linear](https://linear.app/egor-fogel/project/podhod-0fb97512cb40).

Принятый проект бэкенда EGO-9: [модель данных и сценарии](docs/backend.md), [API](docs/api.md), [бюджетный деплой](docs/deployment.md), [ADR-002](docs/adr/002-backend.md). Продуктовые endpoint ещё предстоит реализовать; текущий API содержит health/readiness и маршруты регистрации, сессий, профиля и устройств.

Задачи EGO-18–EGO-34 и ранняя проверка PWA EGO-8: [порядок реализации](docs/implementation-plan.md). Актуальные статусы — в Linear.

Актуальная архитектура доступа: [ADR-003](docs/adr/003-authentication.md). EGO-21 реализует самостоятельную регистрацию с почтой, логином и паролем без рассылки; Telegram-бот, Яндекс ID и VK ID предусмотрены как отдельные будущие интеграции EGO-35–EGO-37. SQL/OpenAPI и формы парольного доступа реализуются в EGO-21; внешние способы пока остаются проектом.

Пользователь разрешил выполнять задачи принятого плана последовательно без промежуточного ревью: после проверок — коммит и push с номером Linear, Done и переход к следующей задаче.
