# Бюджетный деплой и эксплуатация

Дата: 10 октября 2026. EGO-9. Статус: проект принят пользователем; сервер, домен и провайдер пока не выбраны, деплой не выполнен. Основание — [ADR-002](adr/002-backend.md).

## Первый production

Для единиц пользователей предлагаем один Linux VPS с 2 vCPU, 2 GiB RAM и 25–40 GiB SSD как исходный ориентир, проверяем по нагрузке и обработке фото. Если память/бюджет не сходятся, уменьшаем параллелизм worker, а не убираем резервные копии. Один домен, TLS, один origin для web и `/api`; PostgreSQL в закрытой Docker сети. Object storage вне VPS — приватные фото и бэкапы. Почта через транзакционный сервис: собственный SMTP на VPS не закладываем.

Ежемесячные расходы = VPS + object storage (объём, операции, исходящий трафик) + почта сверх бесплатной квоты; домен оплачивается отдельно за год. Для старта выбираем почтовый тариф с небольшой бесплатной квотой и object storage без обязательного крупного минимального платежа. Конкретные цены, доступность региона, способы оплаты и лимиты проверяем непосредственно перед покупкой; это документ без неподтверждённой цены или выбранного провайдера. Не требуются Kubernetes, отдельный Redis, платная управляемая БД или CDN на первом этапе.

Критерии выбора: регион и допустимость хранения личных фото, автоматический внешний backup, доступ к Docker и диску, S3 API/checksum/CORS, лимиты исходящего трафика и бюджета, SMTP/API доставка на нужные почтовые домены. Бесплатные sleeping/serverless сервисы не основной вариант для worker напоминаний. Покупка и создание ресурсов — отдельное согласованное действие после выбора конкретного предложения.

## Сервисы и конфигурация

Будущий `compose.production.yaml` содержит `proxy` (Caddy с автоматическим TLS как предлагаемый вариант), `web` (существующий Nginx), `api`, `worker`, `postgres`. Одноразовый `migrate` запускается перед релизом; автоматические миграции одновременно из API и worker запрещены. Только proxy публикует 80/443. SSH ограничен ключами и доступом оператора, БД наружу не публикуется.

Существующий compose.yaml — локальная основа без БД/TLS/push, этот проект его не превращает в production. Когда появится потребитель БД, добавить локальные PostgreSQL и S3 emulator отдельным dev profile; тестовые записи создаются только тестами, не продуктовым seed.

| Настройка / секрет                                        | Где используется                                              |
| --------------------------------------------------------- | ------------------------------------------------------------- |
| PUBLIC_ORIGIN, HTTP_ADDR, TRUSTED_PROXY_CIDRS             | origin, bind, проверка proxy headers                          |
| DATABASE_URL                                              | отдельные credentials API, worker, migrate, backup            |
| SESSION/LOGIN_HMAC_KEY, JOB_ENCRYPTION_KEY                | коды, защищённый payload очереди; cookie токен хранится хешем |
| S3_ENDPOINT, REGION, BUCKET, S3_ACCESS_KEY, S3_SECRET_KEY | отдельные права media, export, backup                         |
| MAIL_API_KEY, MAIL_FROM                                   | транзакционные письма                                         |
| VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT        | Web Push                                                      |
| BACKUP_ENCRYPTION_KEY, BACKUP_BUCKET                      | внешний зашифрованный backup                                  |
| LIMITS, LOG_LEVEL, RELEASE_SHA                            | бюджет, диагностика, версия                                   |

Секреты находятся в защищённых файлах вне checkout/образа, монтируются read-only; Go поддержит чтение `_FILE`. В Git только имена и example без значений. Не передавать секреты фронту через VITE переменные. Разные секреты/buckets staging и production. Роли БД минимальны: migration DDL, runtime ограниченный DML, cleanup отдельно; права к завершённым ревизиям ограничены. API соединения через pool (начально до 10), worker до 4; общий предел меньше max_connections БД.

Volumes: PostgreSQL data и состояние TLS. Фото не в web root. Контейнеры приложения non-root, read-only filesystem, временная директория ограничена. Worker обрабатывает один файл за раз, декодирование ограничено памятью/временем. Go runtime image должен включать корневые CA и timezone данные (текущий scratch имеет CA, но IANA tzdata надо добавить или embed time/tzdata). Reverse proxy сохраняет внешний HTTPS scheme; доверяем X-Forwarded-* только от заданного proxy, иначе возможны ошибочные cookies, IP limits и redirects.

## CI и выпуск

Существующий checks.yml уже проверяет Go, web и сборки контейнеров. После реализации расширить его проверкой OpenAPI, SQL миграций на временной PostgreSQL, интеграционными тестами ownership/idempotency/conflicts и контейнерным smoke. Образы собираются из принятого коммита, сохраняются в registry с digest и RELEASE_SHA; production не строит из произвольной рабочей директории. Проверка зависимостей и образов перед выпуском, фиксируем используемые версии.

Порядок одного релиза:

1. Выполнить проверки, собрать web и Go API/worker, получить неизменяемые digest. Развернуть в staging и проверить вход/запись/фото/push тест.
2. Проверить свежий внешний backup и свободный диск; сохранить предыдущие digest и версию схемы.
3. Запустить migrate с отдельной ролью и lock; только совместимые расширения схемы. При ошибке остановить выпуск.
4. Остановить приём новых задач worker, завершить/освободить lease; перезапустить API и worker на новых образах. Для первого VPS возможен краткий простой, клиент сохраняет pending ввод.
5. Проверить readiness, вход email, запись тестового подхода в отдельном тестовом аккаунте, получение результата, worker и отсутствие 5xx. Выпустить web после совместимого API.
6. При ошибке вернуть предыдущий образ, если схема совместима. Не запускать destructive down migration для возврата приложения. Если повреждены данные, остановить запись и отдельно восстановить копию с согласованием потери изменений.

Релиз запускается оператором вручную либо позднее через защищённый CI environment с явным действием; проектирование не включает публикацию. Сначала вводим воспроизводимый runbook, потом автоматизацию. HTML макеты design/ не входят в production образ.

## Резервные копии и восстановление

Начальный бюджетный режим: ночной `pg_dump` с внешней зашифрованной копией, retention 7 ежедневных и 4 еженедельных. Цель RPO до 24 часов, RTO до 4 часов **после успешной учебной проверки**; сейчас это цели, не измеренная гарантия. Snapshot VPS полезен дополнительно, не заменяет внешний backup. Ключ дешифрования хранится отдельно от единственного VPS и копии.

Для photos нужны versioning/retention storage либо отдельная внешняя копия; совместимость провайдера проверяется. После дампа сохраняем manifest всех referenced ready объектов, проверяем их наличие и сохраняем требуемые версии в backup prefix с тем же retention. На время формирования manifest исключаем физическую очистку объектов или держим grace не менее 7 дней; tombstones в приложении действуют сразу. Если versioning отсутствует, копирование фотографий в отдельный bucket/аккаунт обязательно. Текущие метаданные без самих файлов не являются полной резервной копией.

Ежемесячно и перед первой приёмкой восстанавливаем копию на чистом окружении: PostgreSQL, referential integrity, фото из manifest, сессии/подписки, история. После аварийного восстановления старые сессии отзываем, jobs/deliveries пересчитываем, истёкшие письма и напоминания не отправляем. Применяем отдельный реестр удалений аккаунтов до открытия доступа. Проверяем secrets/VAPID и credentials, домен/TLS, доступность файлов, только затем возвращаем трафик. Пользователям сообщаем реальный интервал потери данных; локальные pending commands сверяются, не отбрасываются.

Если потребуется RPO меньше суток, добавить архивирование WAL + base backup/PITR. [Документация PostgreSQL](https://www.postgresql.org/docs/current/continuous-archiving.html) описывает восстановление по WAL; это отдельная настройка и проверка, ежедневный dump её не обеспечивает. Уведомление об отсутствии свежего backup обязательно, иначе ошибка может оставаться незаметной.

## Наблюдение и безопасность эксплуатации

JSON logs с requestId, release, route, status, duration и внутренним user ID при необходимости. Не писать email-коды, cookies, Authorization, push endpoints, подписанные URL, тела заметок и фото. Метрики: p95 API, доля 5xx, DB pool/latency, oldest ready job, dead jobs, push accepted/failed (не delivery на телефон), photo failure, свободные диск/RAM, возраст backup. Внешний uptime-check для HTTPS и сигнал оператору при backup >26 часов, dead jobs, малом диске (<20%) и недоступности. Канал уведомлений оператора выбрать при внедрении, не заявлять настроенным заранее.

Ежемесячный maintenance: security обновления ОС и контейнеров, контроль сертификата, restore test, квоты хранения/почты, cleanup и стоимость. Бэкап перед изменением major PostgreSQL, отдельная процедура upgrade, не плавающий docker tag latest. Публичные ручки ограничены по body/rate/time; private storage и least privilege, TLS к внешним сервисам и БД при выходе за локальную закрытую сеть. Доступ администрирования — через SSH/VPN, не продуктовую панель на открытом endpoint.

## Когда усложнять инфраструктуру

При нехватке памяти фото первым переносится worker или увеличивается VPS. При неприемлемом простое БД — managed PostgreSQL с проверенным PITR, затем два stateless API экземпляра за proxy. Объекты уже внешние, jobs разделяются lease. Большие отчёты оптимизируются после EXPLAIN/измерений. Решение о Redis/брокере принимается только при измеренной нагрузке или новых требованиях, без переписывания программы и истории.

Критерии готовности выпуска: домен и TLS; работа email без утечек/перебора; установка PWA; реальный push на целевых устройствах; ownership; офлайн восстановление; повтор команд; backup **и restore**; приватные фото; простой и rollback проверены. Один green CI не подтверждает эти эксплуатационные требования.
