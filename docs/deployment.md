# Бюджетный деплой и эксплуатация

Дата: 10 октября 2026. EGO-9. Статус на 11 октября 2026: пользователь развернул сервис на VDSina, домен podhod-app.duckdns.org. HTTPS health/readiness и HTTP → HTTPS подтверждены выводом команд пользователя; пользователь подтвердил работу сервиса. Резервные копии и restore по его решению пока отложены (EGO-34), проверки PWA/push и окончательная приёмка остаются открытыми. Основание — [ADR-002](adr/002-backend.md).

## Первый production

По уточнению пользователя выбираем небольшой Linux VPS: исходный профиль 1 vCPU, 2 GiB RAM, 25 GiB SSD; пригодность проверяем по нагрузке и обработке фото. [ADR-004](adr/004-small-vps.md) заменяет отдельное хранилище рабочих фотографий приватным диском VPS. Внешние зашифрованные резервные копии БД и файлов сохраняются. Один домен, TLS, один origin для web и `/api`; PostgreSQL в закрытой Docker сети. По [ADR-003](adr/003-authentication.md) регистрация/пароль не требуют почтового сервиса; домен нужен для HTTPS/PWA.

Ежемесячные расходы = VPS + object storage (объём, операции, исходящий трафик); домен оплачивается отдельно за год. Для старта выбираем object storage без обязательного крупного минимального платежа. Конкретные цены, доступность региона, способы оплаты и лимиты проверяем непосредственно перед покупкой; это документ без неподтверждённой цены или выбранного провайдера. Не требуются Kubernetes, отдельный Redis, платная управляемая БД, рассылка или CDN на первом этапе.

Критерии выбора: регион и допустимость хранения личных фото, автоматический внешний backup, доступ к Docker и диску, S3 API/checksum/CORS, лимиты исходящего трафика и бюджета. Бесплатные sleeping/serverless сервисы не основной вариант для worker напоминаний. Покупка и создание ресурсов — отдельное согласованное действие после выбора конкретного предложения.

## Сервисы и конфигурация

`compose.production.yaml` содержит `proxy` (Caddy с автоматическим TLS), `web` (Nginx), `api`, `worker`, `db`. Одноразовый `migrate` запускается перед релизом; автоматические миграции одновременно из API и worker запрещены. Только proxy публикует 80/443. SSH ограничен ключами и доступом оператора, БД наружу не публикуется. Private сети upstream/database отделены от исходящего доступа API/worker. Caddy направляет `/api/*` непосредственно в API, остальные запросы — в статический web; внешний X-Forwarded-For не принимается как доверенный от клиента.

`compose.yaml` — локальное окружение с PostgreSQL, миграциями, API, worker и web, без публичного TLS и готового push. Production запускается отдельным файлом, без объединения с локальным compose. Тестовые записи создаются только тестами, не продуктовым seed.

| Настройка / секрет                                        | Где используется                                                                  |
| --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| PUBLIC_ORIGIN, HTTP_ADDR, TRUSTED_PROXY_CIDRS             | origin, bind, проверка proxy headers                                              |
| DATABASE_URL                                              | отдельные credentials API, worker, migrate, backup                                |
| SESSION/AUTH_HMAC_KEY, JOB_ENCRYPTION_KEY                 | CSRF/ключи лимитов/flows, защищённый payload очереди; cookie токен хранится хешем |
| S3_ENDPOINT, REGION, BUCKET, S3_ACCESS_KEY, S3_SECRET_KEY | отдельные права media, export, backup                                             |
| TELEGRAM_BOT_TOKEN, TELEGRAM_WEBHOOK_SECRET               | Будущая интеграция бота, только при её включении                                  |
| YANDEX/VK_CLIENT_ID, CLIENT_SECRET, REDIRECT_URI          | Будущие адаптеры внешнего входа, только при включении                             |
| VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT        | Web Push                                                                          |
| BACKUP_ENCRYPTION_KEY, BACKUP_BUCKET                      | внешний зашифрованный backup                                                      |
| LIMITS, LOG_LEVEL, RELEASE_SHA                            | бюджет, диагностика, версия                                                       |

Секреты находятся в защищённых файлах вне checkout/образа, монтируются read-only; Go поддержит чтение `_FILE`. В Git только имена и example без значений. Не передавать секреты фронту через VITE переменные. Разные секреты/buckets staging и production. Роли БД минимальны: migration DDL, runtime ограниченный DML, cleanup отдельно; права к завершённым ревизиям ограничены. API соединения через pool (начально до 10), worker до 4; общий предел меньше max_connections БД.

Volumes: PostgreSQL data и состояние TLS. Приватный каталог файлов подключается в EGO-30, когда появится реальный потребитель; фото не в web root. Контейнеры приложения non-root, read-only filesystem, временная директория ограничена. Worker обрабатывает один файл за раз, декодирование ограничено памятью/временем. Go scratch содержит CA, IANA timezone уже встроены через time/tzdata. Reverse proxy сохраняет внешний HTTPS scheme; доверяем X-Forwarded-* только от заданной upstream подсети. Её CIDR надо проверить на отсутствие пересечений с сетями VPS/VPN.

## CI и выпуск

Существующий checks.yml уже проверяет Go, web и сборки контейнеров. После реализации расширить его проверкой OpenAPI, SQL миграций на временной PostgreSQL, интеграционными тестами ownership/idempotency/conflicts и контейнерным smoke. Образы собираются из принятого коммита, сохраняются в registry с digest и RELEASE_SHA; production не строит из произвольной рабочей директории. Допускается сборка конкретного git archive на доверенной машине и передача docker save/load через SSH; API/web тогда закрепляются по полному локальному image ID sha256, запуск — с --pull never. Проверка зависимостей и образов перед выпуском, фиксируем используемые версии.

Порядок одного релиза:

1. Выполнить проверки, собрать web и Go API/worker, получить неизменяемые digest. Развернуть в staging и проверить вход/запись/фото/push тест.
2. Проверить свежий внешний backup и свободный диск; сохранить предыдущие digest и версию схемы.
3. Запустить migrate с отдельной ролью и lock; только совместимые расширения схемы. При ошибке остановить выпуск.
4. Остановить приём новых задач worker, завершить/освободить lease; перезапустить API и worker на новых образах. Для первого VPS возможен краткий простой, клиент сохраняет pending ввод.
5. Проверить readiness, регистрацию и вход по паролю, запись тестового подхода в отдельном тестовом аккаунте, получение результата, worker и отсутствие 5xx. Выпустить web после совместимого API.
6. При ошибке вернуть предыдущий образ, если схема совместима. Не запускать destructive down migration для возврата приложения. Если повреждены данные, остановить запись и отдельно восстановить копию с согласованием потери изменений.

Релиз запускается оператором вручную либо позднее через защищённый CI environment с явным действием; проектирование не включает публикацию. Сначала вводим воспроизводимый runbook, потом автоматизацию. HTML макеты design/ не входят в production образ.

## Резервные копии и восстановление

Начальный бюджетный режим: ночной `pg_dump` с внешней зашифрованной копией, retention 7 ежедневных и 4 еженедельных. Цель RPO до 24 часов, RTO до 4 часов **после успешной учебной проверки**; сейчас это цели, не измеренная гарантия. Snapshot VPS полезен дополнительно, не заменяет внешний backup. Ключ дешифрования хранится отдельно от единственного VPS и копии.

По ADR-004 для фото на диске VPS нужна внешняя копия файлов вместе с дампом и manifest всех referenced ready объектов. Финальные файлы неизменяемы; проверяем наличие/checksum и сохраняем их с тем же retention. На время формирования копии исключаем физическую очистку или держим grace не менее 7 дней; tombstones в приложении действуют сразу. Рабочие pending файлы не подменяют ready объекты. При переходе на S3 нужны versioning/retention либо копирование фотографий в отдельный backup bucket/аккаунт. Метаданные без самих файлов не являются полной резервной копией.

Ежемесячно и перед первой приёмкой восстанавливаем копию на чистом окружении: PostgreSQL, referential integrity, фото из manifest, сессии/подписки, история. После аварийного восстановления старые сессии отзываем, jobs/deliveries пересчитываем, истёкшие письма и напоминания не отправляем. Применяем отдельный реестр удалений аккаунтов до открытия доступа. Проверяем secrets/VAPID и credentials, домен/TLS, доступность файлов, только затем возвращаем трафик. Пользователям сообщаем реальный интервал потери данных; локальные pending commands сверяются, не отбрасываются.

Если потребуется RPO меньше суток, добавить архивирование WAL + base backup/PITR. [Документация PostgreSQL](https://www.postgresql.org/docs/current/continuous-archiving.html) описывает восстановление по WAL; это отдельная настройка и проверка, ежедневный dump её не обеспечивает. Уведомление об отсутствии свежего backup обязательно, иначе ошибка может оставаться незаметной.

## Наблюдение и безопасность эксплуатации

JSON logs с requestId, release, route, status, duration и внутренним user ID при необходимости. Не писать пароли, auth state/nonce/verifier, provider tokens, cookies, Authorization, push endpoints, подписанные URL, тела заметок и фото. Метрики: p95 API, доля 5xx, DB pool/latency, oldest ready job, dead jobs, push accepted/failed (не delivery на телефон), photo failure, свободные диск/RAM, возраст backup. Внешний uptime-check для HTTPS и сигнал оператору при backup >26 часов, dead jobs, малом диске (<20%) и недоступности. Канал уведомлений оператора выбрать при внедрении, не заявлять настроенным заранее.

Ежемесячный maintenance: security обновления ОС и контейнеров, контроль сертификата, restore test, квоты хранения, cleanup и стоимость. Бэкап перед изменением major PostgreSQL, отдельная процедура upgrade, не плавающий docker tag latest. Публичные ручки ограничены по body/rate/time; private storage и least privilege, TLS к внешним сервисам и БД при выходе за локальную закрытую сеть. Доступ администрирования — через SSH/VPN, не продуктовую панель на открытом endpoint.

## Когда усложнять инфраструктуру

При нехватке памяти фото первым переносится worker или увеличивается VPS. При неприемлемом простое БД — managed PostgreSQL с проверенным PITR, затем два stateless API экземпляра за proxy. Объекты уже внешние, jobs разделяются lease. Большие отчёты оптимизируются после EXPLAIN/измерений. Решение о Redis/брокере принимается только при измеренной нагрузке или новых требованиях, без переписывания программы и истории.

Критерии готовности выпуска: домен и TLS; регистрация и парольный вход без утечек/перебора; установка PWA; реальный push на целевых устройствах; ownership; офлайн восстановление; повтор команд; backup **и restore**; приватные фото; простой и rollback проверены. Один green CI не подтверждает эти эксплуатационные требования.
