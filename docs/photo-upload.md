# Загрузка фотографий: две на дату

11 октября 2026, EGO-44. Существующая загрузка reserve → PUT → complete → worker и приватная галерея сохранены. На одну дату дневника каждого пользователя допускается максимум две неудалённые фотографии; pending, processing и failed занимают место. Удаление освобождает место сразу, физическая очистка остаётся отложенной. Перенос в заполненный день отклоняется. Повтор существующей загрузки не занимает новое место, повтор команды возвращает сохранённый receipt.

Сервер возвращает 409 photo_day_quota с понятным сообщением. Записи сериализованы существующей блокировкой пользователя в httpx.Core.Command; лимит проверяется внутри той же транзакции при резервировании и переносе. Старые фото не удаляются, диапазон position 1–20 остаётся для совместимости с прежними данными. Миграция БД не требуется.

Интерфейс показывает максимум 2 фото на день, блокирует новое добавление при заполнении и до загрузки списка, сохраняет удаление и повтор отправки. После ошибки отправки перечитывает список, чтобы учитывать уже созданную pending-запись. Конкретное сообщение сервера при 409 отображается без подмены ошибкой версии. Поддерживаются JPEG/PNG/WebP до 10 MiB; HEIC в этом изменении не добавлен.

Проверки: npm run check и production build; go test -race ./internal/media ./internal/httpx на Linux с отдельной PostgreSQL 18.6. Проверены полный upload/worker/private pipeline, две конкурентно успешные резервации и два отказа, запрет третьего pending/failed/processing фото, повтор загрузки при полном дне, удаление/перенос, idempotency и изоляция аккаунтов; гонка двух переносов в день с одним свободным местом допускает один перенос. Нативный запуск на macOS не подходит для upload: существующее filesystem storage поддерживает Linux/Windows. Свежая браузерная проверка интерфейса этим проходом не проводилась.

Изменение пока локальное, на VDS не развёрнуто. Для сервера потребуются новые образы API/worker и web; данные и секреты сохраняются. Резервные копии по решению пользователя пока не выполняются.
