# План разработки «Подход»

Linear — источник статусов. Этот документ описывает порядок, не заменяет живые задачи.

| Этап                    | Задачи              | Результат                                                         |
| ----------------------- | ------------------- | ----------------------------------------------------------------- |
| 1. Требования и дизайн  | EGO-5, EGO-6, EGO-7 | Правила, сценарии и рассматриваемые пользователем макеты двух тем |
| 2. Техническая проверка | EGO-8, EGO-9        | Реальная установка/push и обоснованная архитектура                |
| 3. Основа               | EGO-10, EGO-11      | React + TS, дизайн-система, API и сохранение данных               |
| 4. Тренировочный цикл   | EGO-12, EGO-13      | Программа → тренировка → подходы → отдых → итог                   |
| 5. Дневник и прогресс   | EGO-14, EGO-15      | Месячный календарь, фото, заметки, графики фактов                 |
| 6. Надёжность и выпуск  | EGO-16, EGO-17      | Офлайн, напоминания, проверка на устройствах и выпуск             |

Проверку PWA нужно провести рано, а не отложить риск push до выпуска. EGO-8 использует минимальную техническую инфраструктуру, не требует реализации всего backend. EGO-16 применяет её результат в приложении.

Frontend утверждён: React + TypeScript, архитектура FSD. В EGO-10 инициализирован единый репозиторий с Go API; границы и причины описаны в ADR-001. Проект backend EGO-9 принят пользователем: PostgreSQL, email-коды, Go worker, приватное object storage и бюджетный VPS зафиксированы в ADR-002. [Конкретный порядок реализации](implementation-plan.md): EGO-18–EGO-34 с ранней проверкой EGO-8 после HTTPS окружения. Следующая задача — EGO-18; остальные идут по зависимостям. Не добавлять сложную распределённую инфраструктуру без необходимости.

Remote: git@github.com:fogel-dev/podhod.git. Git и origin настроены; перед фиксацией EGO-9 удалённый main проверен и содержит коммит EGO-10. После принятия задачи пользователем — коммит и пуш с описательным русским сообщением и номером Linear.

Задачи крупные и имеют критерии приёмки. При начале реализации разбивать конкретную задачу на подзадачи по необходимости, вместо создания десятков спекулятивных задач заранее.
