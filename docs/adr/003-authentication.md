# ADR-003: регистрация и несколько способов входа

Дата: 10 октября 2026. Linear: EGO-21. Статус: решение по запросу пользователя; реализация в EGO-21. Заменяет часть ADR-002 о входе по email-коду. Остальные решения ADR-002 действуют.

## Первая версия

Самостоятельная регистрация: почта, логин, пароль, подтверждение пароля. Вход — логин и пароль. Отправки писем пока нет; почта сохраняется как неподтверждённая. Подтверждение пароля проверяется клиентом и сервером, нигде не хранится. Нет публичного сброса пароля по неподтверждённой почте. Смена пароля из действующей сессии требует текущий пароль и отзывает остальные сессии. Потерянный пароль до подключения альтернативного входа требует помощи оператора с независимой проверкой владельца; знание email не доказывает владение.

Логин: 3–32 символа ASCII, первая буква, далее буквы, цифры и `_`; trim и нижний регистр, UNIQUE. Почта: валидный адрес до 254 символов, trim и нижний регистр по правилу продукта, без удаления точек или `+suffix`. Не объединяем адреса по правилам отдельных почтовых сервисов. Для неподтверждённой почты нет UNIQUE: чужой введённый адрес не должен занимать почту владельца. Уникальный частичный индекс действует только на подтверждённые адреса. До проверки почты вход только по логину; сообщение о занятом логине не раскрывает почту. Изменение адреса сбрасывает подтверждение.

Пароль: 15–128 символов Unicode, без обязательного набора классов; пробелы допустимы, не trim и не нормализовать. Хеш Argon2id с отдельной случайной солью и параметрами в PHC-строке. Исходная конфигурация: 19 MiB, две итерации, один поток, соль 16 байт и результат 32 байта; измерить время на выбранном VPS. Увеличивать параметры по результатам измерений, обновлять хеш после успешного входа. Ограничить параллельные вычисления хеша, размер тела и частоту запросов. Политика хранения основана на [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Лимиты в PostgreSQL работают между экземплярами API: первоначально вход до 10 попыток за 15 минут на логин и 60 на IP, регистрация до 5 за час на IP; значения конфигурируемые. Неизвестный логин проходит эквивалентную проверку dummy-хеша, ответ совпадает с неверным паролем. IP определяем только с учётом доверенного proxy; ключ лимита HMAC, не открытая почта/IP. Отсутствует вечная блокировка аккаунта из-за чужих попыток. CAPTCHA пока не нужна, но открытая регистрация требует наблюдения за злоупотреблениями.

## Данные и границы модулей

Тренировки, фотографии, устройства и сессии ссылаются только на внутренний `users.id`. Пароль и внешние идентификаторы не становятся владельцами данных. Один пользователь может подключить несколько способов входа.

| Таблица                | Данные и ограничения                                                                                                                                                                                                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `users`                | UUID, уникальный `login_normalized`, nullable `email_normalized`, `email_verified_at`, timezone/locale/status/version. Первичная регистрация требует email, будущий внешний аккаунт может не иметь email. UNIQUE email только WHERE email_verified_at IS NOT NULL                                                  |
| `password_credentials` | `user_id` PK/FK, `password_hash`, `changed_at`. Не более одного пароля; отдельная таблица позволяет будущему аккаунту не иметь пароль                                                                                                                                                                              |
| `auth_identities`      | UUID, user_id, provider (`telegram`, `yandex`, `vk`), `subject text`, created_at/last_used_at. UNIQUE(provider, subject), UNIQUE(user_id, provider). Subject — постоянный ID, username/display name только отображение                                                                                             |
| `auth_flows`           | UUID, provider, purpose (`login`, `link`, `reauth`, `delete_account`), initiating_user_id/session_id для привязки и подтверждения, хеши state/секрета браузера/deep-link nonce, зашифрованный PKCE verifier, подтверждённый subject, expires_at, consumed_at/status. TTL 5 минут, одноразовое атомарное завершение |
| `auth_rate_limits`     | Ключ HMAC области/IP/логина, окно, счётчик, expires_at. Атомарный upsert и ограниченная очистка                                                                                                                                                                                                                    |
| `sessions` / `devices` | Общие для всех способов входа; сессия хранит token_hash, csrf_hash, expires_at/revoked_at и last_authenticated_at                                                                                                                                                                                                  |
| `auth_events`          | Минимальный журнал login/link/unlink/password_changed/revocation: user_id?, provider?, результат и время. Не хранить пароли, коды, токены, webhook bodies и provider payload                                                                                                                                       |

Это целевая схема, а не заявление о применённых миграциях. Уже применённую `001_foundation.sql` не менять: последующая миграция добавит профиль/credentials, снимет UNIQUE неподтверждённой почты и удалит неиспользуемую `login_challenges`. Будущие таблицы flow/identity вводить при появлении потребителя; пустые интеграции и скрытые фиктивные ручки не нужны.

Go-модуль `auth` отвечает за credentials, лимиты, реаутентификацию и выдачу сессии; `accounts` — профиль и способы входа. Адаптеры `telegram`, `yandex`, `vk` проверяют доказательство провайдера и возвращают `{provider, subject}`. Только серверный адаптер формирует такую структуру; JSON клиента не является доказательством. Общий сервис транзакционно разрешает identity в users.id и создаёт сессию. Bot webhook остаётся в том же Go-приложении, отдельный сервис/брокер не требуется. FSD: features/password-auth и позднее features/external-auth, профиль entities/user, transport shared/api.

## Сессии и привязка

Криптографически случайный токен выдаётся в `__Host-podhod_session`; HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, 30 дней. В БД только хеш. Origin проверяется и на публичных POST регистрации/входа, а на приватных мутациях дополнительно CSRF. Cookie и токены не попадают в IndexedDB/localStorage; офлайн сохраняются только разрешённые тренировочные данные. Смена пользователя очищает локальные приватные данные предыдущего аккаунта. Регистрация создаёт user, credential, sync_head, device и session одной транзакцией. Cookie выдаётся только после commit.

Подключение внешнего способа начинается из настроек текущего аккаунта после свежего подтверждения паролем или уже подключённым провайдером (не старше 5 минут). Flow фиксирует user_id и session_id; callback не может выбрать другого пользователя. Внешняя identity, занятая другим аккаунтом, даёт конфликт без переноса истории. Отключение требует свежего подтверждения и не разрешено для последнего доступного способа. Изменения списка способов сериализуются блокировкой пользователя. Почта от провайдера, даже подтверждённая, сама по себе не связывает аккаунты. Слияние двух уже созданных аккаунтов — отдельная будущая функция с доказательством доступа к обоим, сейчас отсутствует.

Если внешняя identity ещё не привязана, клиент предлагает войти в существующий аккаунт и подключить её либо явно создать новый с выбором уникального логина. Email и пароль при внешней регистрации могут отсутствовать. Незавершённый внешний flow не создаёт пользователя. Браузеру не передаются access/refresh tokens; если нужны только для получения subject, не сохраняем после проверки. Подключённый провайдер может служить подтверждением при установке нового пароля.

## Telegram: вход через нашего бота

1. Браузер POST создаёт login/link flow. Сервер выдаёт `https://t.me/<bot>?start=<nonce>` и HttpOnly cookie привязки к этому браузеру. Nonce случайный 32 байта в base64url, без user_id/email/сессионного токена. В БД только его хеш. [Telegram поддерживает такой deep link](https://core.telegram.org/bots/features#deep-linking); параметр до 64 символов.
2. Бот получает `/start nonce` в личном чате. Принимаем числовой Telegram `from.id` как subject строкой, а не username/номер телефона. Вход не завершается от одного открытия ссылки: бот предлагает явное подтверждение и показывает короткий код, совпадающий с исходным экраном приложения, назначение и время запроса. Не просим пароль приложения в Telegram.
3. Webhook проверяет `X-Telegram-Bot-Api-Secret-Token`, HTTPS, размер тела, повтор update_id и приватный чат. Подтверждение callback_query принимается только от того же Telegram user, который начал flow. Bot token и webhook secret хранятся вне checkout. Требования транспорта описаны в [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).
4. Подтверждение связывает flow с проверенным Telegram subject, но ещё не выдаёт сессию. Исходный браузер опрашивает status не чаще раза в две секунды, только пока экран открыт, и показывает подтверждённый аккаунт для финального подтверждения. Завершение — отдельный POST с cookie браузера; чужой браузер/пересланная ссылка не могут забрать сессию. Не переносим cookie из Telegram webview: пользователь возвращается в первоначальную PWA.
5. В одной транзакции consume flow, привязка identity или выдача сессии. Истёкший, использованный, отменённый flow повторно не работает. После потери ответа без cookie нужен новый flow. Telegram down не препятствует паролю; отсутствие bot credentials скрывает кнопку входа. TTL/cleanup ограничивают хранение временных subject.

Deep link содержит чувствительный одноразовый nonce: no-store, Referrer-Policy no-referrer, отсутствие аналитики и логирования query на этих маршрутах. Пересылка ссылки не является безопасным способом приглашения. Отдельный код сравнения и подтверждение в обоих интерфейсах уменьшают риск подтверждения чужого входа.

## Яндекс ID и VK ID

Оба провайдера подключаются самостоятельными адаптерами, а не Telegram-протоколом. Выбираем authorization code flow, случайный state, PKCE S256, callback URI из фиксированного списка, серверный обмен code на token и проверку профиля у официального endpoint. Flow привязан к cookie исходного браузера; callback сравнивает provider, state, TTL и purpose. После callback короткий redirect на наш путь без code/state в адресе; Referrer-Policy no-referrer. Open redirect запрещён: returnTo только разрешённый локальный путь. При использовании OIDC нужны проверки подписи, issuer, audience, exp и nonce; нельзя просто декодировать JWT.

У Яндекса подтверждена поддержка state и PKCE в [официальном code flow](https://yandex.ru/dev/id/doc/en/codes/code-url). В [официальном VK ID SDK](https://github.com/VKCOM/vkid-web-sdk) есть state/codeVerifier; конкретные endpoint, device_id, требования SDK и проверку токенов сверить при реализации по актуальной спецификации. Портал id.vk.com при проверке не открылся, поэтому переносить предполагаемые детали старого VK OAuth в код запрещено. OAuth и Telegram адаптеры не подменяются друг другом; общий только результат подтверждения и управление аккаунтом.

Для каждого нужны зарегистрированное приложение, разрешённый HTTPS callback, credentials и реальная проверка входа/отзыва. Минимальные scopes для идентификации; телефон и контакты не запрашивать. Кнопку включать только после рабочей конфигурации и приёмки провайдера. Будущие интеграции — отдельные задачи Backlog, не условие готовности парольной регистрации.

## API и изменение старого контракта

Первая версия: POST `/auth/register` (email, login, password, passwordConfirmation, deviceLabel), POST `/auth/login` (login, password, deviceLabel), GET `/auth/session`, POST `/auth/logout`, POST `/auth/password/change`, GET/PATCH `/me`, GET `/me/devices`, DELETE `/me/devices/{id}`. Приватные мутации — CSRF; редактирование профиля/отзыв устройства — If-Match. Ошибки регистрации: 422 field errors; занятый логин — 409. Сессия едина для всех провайдеров. `GET /me` не выдаёт credential hash и чужие identities.

Будущие: GET `/auth/providers` (только доступные способы), POST `/auth/flows` (provider/purpose/returnTo), GET `/auth/flows/{id}`, POST `/auth/flows/{id}/complete`, фиксированные GET callbacks Яндекс/VK, POST `/integrations/telegram/webhook`, GET `/me/identities`, DELETE `/me/identities/{id}`. GET status требует browser binding; link/reauth требуют сессию/CSRF. CSRF при анонимном complete заменяет строгое сочетание Origin и browser binding. Browser binding не раскрывается в JSON/deep link. Детальные DTO добавляются одновременно с реализацией, не обещаем работающие ручки заранее.

Существующий OpenAPI EGO-18 отражает прежний email-код и пока не реализованные продуктовые маршруты. В EGO-21 заменить эти методы/DTO и перегенерировать клиентские типы до подключения формы. Это осознанная смена контракта до первого выпуска, а не обратно совместимое изменение; исключение проверки совместимости должно быть узким, документированным и проверяемым. До этого OpenAPI не считать контрактом новых сценариев. После первого выпуска действует обычное окно поддержки клиентов. Подтверждение удаления аккаунта EGO-33 использует свежую реаутентификацию с purpose=delete_account вместо письма.

## Приёмка

EGO-21: реальная БД, атомарная конкурентная регистрация, правильный/неправильный пароль, unknown login, лимиты, cookie/Origin/CSRF, ownership, смена пароля и отзыв устройств; формы в обеих темах и на 320px. Внешние входы отдельно проверяют потерю/повтор/подмену state, пересылку Telegram nonce, чужой browser, callback replay, login/link confusion, занятый subject, отключение последнего способа и отсутствие автоматического слияния по email. Реальный вход у каждого провайдера обязателен; тестовый transport сам по себе интеграцию не закрывает.
